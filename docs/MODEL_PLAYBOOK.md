# muten-overlay モデル/スキル使い分けプレイブック(個人用)

> **このドキュメントの目的**: このリポジトリでの実際の作業実績
> (DR-1 → DR-11 → DR-2a → DR-5 → DR-3 の一連の「発見→修正→teeth検証→
> ドキュメント化→push」ループ)を根拠に、Claude のどのモデル・どの
> スキルをどの作業に使うべきかを判断する個人用の早見表。すべての行は
> 本セッション/直前セッションで実際に起きたことに紐付いており、
> 一般論ではない。判断に迷ったら「テストが全部緑でも、まだ論理的に
> 誤っている可能性のある箇所を扱っているか?」を最初に自問する —
> これが Fable 5 とそれ以外を分ける最大の分岐点になる。

## 1. モデル使い分け表

| 作業の種類 | 推奨モデル | このリポジトリでの実例 | 理由 |
|---|---|---|---|
| **新規バグの発掘・監査**(まだ誰も指摘していない欠陥を、動いているコードの中から見つける) | **Fable 5** | DR-11: `Monitor::sweep` が「存在」と「出現」を混同していることを、DR-1 の e2e 検証の**副産物として**発見。誰にも指摘されていない状態から気付いた。 | 全テストが緑でも、設計そのものに潜む論理的誤りは最も深い推論でしか拾えない。ここをコストの安いモデルに任せると「テスト green = 完成」という誤った安心感で本番に欠陥が残る。 |
| **自分が書いた設計・実装の自己レビュー**(コードを書いた直後、テストを書く前に見直す) | **Fable 5** | DR-2a: `age_ms` 推論の初稿(`!was_first_sweep` ゲート)に含まれる「起動時から存在し続けるウィンドウが2スイープ目から誤って `very_new` 扱いされる」バグを、**テストを一度も実行する前に**自己発見。放置していれば偽陽性がそのまま本番に到達していた。 | このプロダクトの設計原則は「false-positive-averse」。偽陽性クラスのバグは表面的なテストでは検出されにくく、実装者自身が最高の推論力で「この設計は本当に全てのケースを covered しているか」を疑う必要がある。 |
| **アーキテクチャ・プロトコル設計判断**(既存の外部インタフェースを拡張する際の設計選択) | **Fable 5 / Opus**(プランモード併用) | DR-1: helper プロトコルに process 名を足す際、「別 verb (`processes`) を追加する」案ではなく「`enumerate` の JSON に埋め込む」案を、TOCTOU 発生リスクとサブプロセス起動コスト2倍という具体的根拠で選定。 | この種の判断は一度実装すると外部プロトコル(helper ↔ daemon の wire format)を変更することになり、後戻りコストが高い。プランモードで一度立ち止まり、複数案を比較検討できる深い推論のモデルを使うべき。 |
| **設計が確定した機能の実装**(仕様・アルゴリズムが固まっている状態でコードに落とす) | **Sonnet** | DR-3 (hot-reload) と DR-5 (chunked sleep) は、設計方針が明確な状態から実装まで一気通貫で Sonnet が実施。速度と正確性のバランスが良く、往復コストを最小化できた。 | 「何を作るか」が決まった後の「どう書くか」は、Fable 5 ほどの推論深度を必要としない。Sonnet で十分な精度が出る上に、反復サイクル(実装→テスト→修正)が速い。 |
| **確立済み手順の反復実行**(teeth検証: fix を一時的に revert → test が red になることを確認 → restore) | **Sonnet**(あるいは Haiku でも可) | 本セッション全体で5回(DR-1, DR-11, DR-2a, DR-5, DR-3)実施した「revert→red確認→restore」の手順は、毎回ほぼ同じ形式的作業。 | 手順自体に発見的推論は不要で、既存のテスト設計方針に忠実に従うだけ。ここに高コストなモデルを使うのは無駄。 |
| **機械的な一括編集**(構造体リテラルへのフィールド追加、テスト件数・バージョン番号の更新、`cargo fmt` が指摘した差分の反映) | **Haiku** | DR-1 で `EnumeratedWindow` に `process` フィールドを追加した際の構造体リテラル約25箇所への `process: None` 追加、CHANGELOG/README のテスト件数の機械的な数値更新。 | パターンが完全に決まっている単純作業。Haiku で品質を落とさず最速・最安に処理できる。ここに Sonnet 以上を使うのはコストの無駄遣い。 |
| **複数プラットフォームにまたがる大規模改修**(DR-2 の残り: X11/macOS/Wayland/Windows 4種の helper の `origin`/`has_close_button`/`blocks_input` 忠実度向上) | **Fable 5 でプラン設計+最終レビュー、Sonnet でプラットフォームごとに実装**のハイブリッド | まだ未着手。FEATURE_AUDIT_2026H2.md で「一度のセッションでは扱わず、プラットフォームごとに分割すべき」と明記済み。 | 4 helper 間の一貫性(wire format・命名規則)を保つ設計判断は Fable 5、各 OS 固有 API(`_NET_WM_STATE_FOCUSED` / `GetTickCount` 等)への機械的な落とし込みは Sonnet、という分業が最も効率的。 |
| **「つづけて改善」の連続自律ループ**(次に何を直すかの選定〜実装〜push を繰り返す) | **Opus(fast mode)または Sonnet**、節目ごとに Fable 5 でドキュメント全体の整合性チェック | 本セッションで5往復実施した DR-1〜DR-3 のループ。 | ループの各サイクル自体は「設計確定 → 実装」の反復なので Sonnet 相当で回せる。ただし audit doc の STATUS 更新や次の優先順位判断は俯瞰的な整合性チェックが要るため、数往復ごとに Fable 5 で棚卸しするとドリフトを防げる。 |

## 2. スキル使い分け表

| スキル | 使いどころ(このリポジトリでの想定) | 実績・根拠 |
|---|---|---|
| **プランモード**(`ExitPlanMode` フロー) | 外部インタフェース(helper プロトコル、CLI フラグ、audit イベントの kind)を変更する前。 | DR-1 と DR-11 の実装前にそれぞれプランモードを使用し、承認を得てから着手。両方とも一度実装すると後戻りコストが高い変更だった。 |
| **`/code-review`** | push 前の diff レビュー、特に「偽陽性を新たに生んでいないか」の独立チェック。 | 本セッションでは自己レビューのみで代替してきたが、今後の DR-2 のような複数ファイル改修では独立視点の `/code-review` を挟む価値が高い。 |
| **`/security-review`** | helper スクリプト(`.sh`/`.ps1`)や daemon のファイル操作(`DaemonLock`, stop-flag, rules hot-reload)に触れた回。 | DR-3 で rules ファイルを daemon が定期的に読み直す変更を入れた際、ファイル操作(symlink 攻撃・TOCTOU 等)の観点は独立レビューで拾える種類の懸念。 |
| **`verify` スキル(実バイナリ + fake helper での e2e 確認)** | ユニットテストだけでなく、コンパイル済みバイナリを実際に動かして確認する場面全て。 | 本セッションの中核手法。DR-1〜DR-3 すべてで `cli_contract.rs` の e2e テスト+実プロセス起動による確認を実施し、複数の実バグ(ゼロイベントクラッシュ、メトリクス書き込み once-only バグ等)を発見済み。テストだけでは「テストの前提自体が間違っている」バグを見逃す。 |
| **`/simplify`** | 大きめの機能追加が一段落した後のクリーンアップ。 | まだ本セッションでは未使用。DR-2(4 helper 改修)完了後のタイミングで有効。 |
| **`deep-research`** | `docs/THREAT_INTEL_2026.md` のような、新しい詐欺手口・脅威動向を外部情報から調査する回のみ。 | 検出ロジック自体の変更には使わない(このプロダクトはオフライン・ML不使用が設計原則のため、web調査は「何を検出すべきか」の根拠集めに限定)。 |
| **`/loop`** | 「つづけて改善」を毎回手動で送る代わりに、一定間隔で自動的に次のサイクルを回したい場合。 | 本セッションはユーザーが毎回手動で「つづけて」と送る運用だったが、同じパターンを自動化したいなら `/loop` に置き換え可能。 |

## 3. 推奨ワークフロー(3段構え)

このリポジトリでの改善サイクルは、実績ベースで次の3段階に分けるのが最も
コスト効率が良い:

1. **Fable 5 — 監査・設計フェーズ**: 次に直すべき real bug を見つける
   (ソクラテス式問答、既存 audit doc の棚卸し)。設計判断が要る場合は
   プランモードを併用。
2. **Sonnet — 実装・検証フェーズ**: 設計が固まった内容をコードに落とし、
   teeth 検証(revert→red確認→restore)・`cargo test`/`clippy`/`fmt` を
   一気通貫で実施。
3. **Haiku — 機械的後処理**: CHANGELOG/README のテスト件数更新、
   構造体リテラルへの一括フィールド追加のような、パターンが完全に
   決まった単純作業。

モデルが何であっても、このリポジトリでは以下は不変則として必ず守る
(本セッション全体を通じて一度も緩めていない):
- teeth 検証(regression test を書いたら、fix を外して red になることを
  確認してから戻す)
- `docs/FEATURE_AUDIT_2026H2.md` の STATUS タグ形式(`RESOLVED`/`OPEN`/
  `VERIFIED-HEALTHY`/`WONTFIX`)を崩さない
- 新規依存ゼロ / `forbid(unsafe_code)` / MSRV 1.75 / offline-first

## 4. コスト感覚の目安

おおよその処理コスト・速度の序列は `Haiku ≪ Sonnet < Opus < Fable 5`。
実績から言えるのは、**「安いモデルで実装し直しになるより、バグ発掘の
一手だけ Fable 5 に払う方がトータルで安い」**という点。DR-2a の
自己発見(テスト実行前に自分の設計ミスに気付いた事例)がその典型で、
もし Sonnet や Haiku がそのまま実装を進めていたら、偽陽性が
teeth 検証をすり抜けて本番相当のコードに混入していた可能性が高い
(revert して確認した際、そのテスト自体は書けていたはずだが、
「そもそも何をテストすべきか」という設計上の見落としは推論の深さで
しか防げない種類の欠陥だった)。
